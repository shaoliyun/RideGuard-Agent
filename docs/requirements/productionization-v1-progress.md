# TaxiAgent 工程化改进阶段总结

## 1. 文档定位

本文总结 TaxiAgent 从“具备多 Agent 业务能力的原型”向“可运行、可恢复、可审计的平台”演进的第一阶段工作。内容基于当前仓库已经落地的代码和配置，不把后续规划当作已完成能力。

本阶段的核心变化可以概括为：

```text
从能完成业务流程
→ 变成能够明确管理配置、状态、风险、依赖和运行结果
```

## 2. 改进总览

| 改进方向 | 之前的问题 | 本阶段方法 | 当前成效 |
| --- | --- | --- | --- |
| 配置安全 | 配置容易依赖本地秘密值，开发者难以区分示例配置和真实配置 | 增加无秘密的环境变量配置模板，并将敏感配置改为外部注入 | 新开发者可以按照模板准备配置；仓库不需要提交真实凭据 |
| 本地运行 | 基础设施依赖较多，缺少统一启动方式 | 增加 Dockerfile、Compose、健康检查和持久化卷 | MySQL、Redis、MongoDB、Elasticsearch 具备统一的本地启动基础 |
| 订单一致性 | 订单确认主要依赖松散的 Redis 标记，状态不清晰，重复确认可能造成重复创建 | 建立显式订单状态、白名单状态迁移、Redis 原子操作和重复创建防护 | 下单流程具备可检查的状态边界，并能拒绝非法跳转和重复副作用 |
| 运行可观测性 | 缺少标准健康检查和 Prometheus 指标，排查问题依赖日志猜测 | 引入 Actuator、Prometheus 基础配置和统一上下文 | 可以区分存活、就绪和指标访问，后续可继续补充业务指标 |
| Capability 扩展 | 工具元数据分散在方法和 Agent 配置中，Agent 依赖手写工具列表 | 增加 Capability 接口、风险级别、权限、确认要求、输入输出类型和 Registry | 新能力可以通过实现接口加入注册中心，Registry 会校验名称唯一性 |
| 外部依赖韧性 | 地图、天气和模型调用缺少统一超时、重试、熔断和限流基线 | 增加 Resilience4j 依赖和统一配置基础 | 为只读调用重试、写操作不重试以及降级策略提供了落点 |
| 自动化验证 | 关键状态和扩展机制缺少确定性测试 | 为订单状态机、Capability Registry 和首个 Capability 增加单元测试 | 核心规则可以脱离外部服务进行快速验证 |

## 3. 分项说明

### 3.1 配置从“本地可用”转向“可安全交付”

#### 之前的问题

项目依赖数据库、缓存、搜索服务和大模型供应商。若把真实连接信息直接写进配置文件，会带来凭据泄露、环境切换困难和部署不可复用等问题。

#### 采用的方法

- 提供 `application-example.yaml` 作为无秘密配置模板。
- 通过环境变量注入数据库、Redis、MongoDB、Elasticsearch 和模型供应商配置。
- 保留生产默认值与本地演示配置的边界，避免把开发便利配置误当成生产配置。

#### 成效

部署者能够先复制配置模板，再根据当前环境填写变量；代码仓库不需要保存有效密钥。后续可以在 CI 中接入秘密扫描，进一步把“凭据不入库”变成自动化检查。

### 3.2 从手动拼装依赖转向容器化本地运行

#### 之前的问题

项目同时使用 MySQL、Redis、MongoDB 和 Elasticsearch。只依赖 README 手工安装时，版本、端口、数据目录和启动顺序容易不一致，新成员难以快速复现环境。

#### 采用的方法

- 增加应用 `Dockerfile`。
- 增加 `compose.yaml`，统一声明基础设施服务。
- 为基础设施配置健康检查和持久化卷。
- 通过服务依赖关系表达基本启动顺序。

#### 成效

项目具备“一套 Compose 配置启动基础依赖”的运行基础。服务重启后数据可以保留，应用容器也有明确的构建入口。该方案仍然是开发和演示环境基础，不代表已经完成生产集群部署。

### 3.3 订单流程从隐式标记转向显式状态机

#### 之前的问题

原有订单确认流程主要依赖 Redis 中的若干标记。标记本身不能完整表达当前阶段，也难以约束非法跳转。在并发确认或重复请求下，可能出现重复执行创建订单的风险。

#### 采用的方法

将订单流程抽象为明确状态：

```text
COLLECTING
  → QUOTED
  → WAITING_CONFIRMATION
  → CREATING
  → CREATED
```

同时定义 `CANCELLED`、`EXPIRED` 和 `FAILED` 等终止状态，并配套：

- 白名单状态迁移规则。
- Redis 原子迁移基础设施。
- 单会话创建权的一次性消费。
- 已创建订单的重复调用保护。
- Redis 不可用时禁止继续创建订单，避免用本地内存掩盖一致性问题。

#### 成效

订单流程从“多个标志位共同决定行为”变成“状态和迁移规则共同决定行为”。非法跳过确认、终止状态重新进入创建流程等情况可以被明确拒绝；并发确认的正确性也有了专门的控制点和测试入口。

需要说明的是，本阶段优先完成了状态机和原子迁移基础设施，完整的端到端并发测试以及 MySQL、MongoDB 之间的补偿机制仍属于后续工作。

### 3.4 从无统一运行信号转向基础可观测性

#### 之前的问题

没有标准化的 readiness、liveness 和 metrics 入口时，部署系统无法可靠判断应用是否已经可以接收请求；开发者也难以从指标角度观察路由、工具调用和订单状态变化。

#### 采用的方法

- 引入 Spring Boot Actuator。
- 引入 Micrometer Prometheus Registry。
- 为后续记录路由次数、工具调用结果、状态迁移次数和耗时保留统一入口。
- 结合 `requestId`、`userId`、`chatId` 等上下文，改善跨 Agent 调用链排查能力。

#### 成效

应用具备健康检查和 Prometheus 指标的基础接入能力，运维系统可以围绕健康状态和指标端点建立探针。当前阶段重点是基础设施接入，完整业务指标覆盖仍需继续补充。

### 3.5 工具从“方法集合”开始演进为 Capability

#### 之前的问题

原有工具主要通过 `@Tool` 暴露，工具名称、输入输出和风险信息分散在方法签名、注解和 Agent 的硬编码列表中。随着工具数量增长，统一做权限校验、确认控制和能力发现会越来越困难。

#### 采用的方法

增加以下抽象：

- `AgentCapability<I, O>`：统一能力输入、输出和执行入口。
- `RiskLevel`：表达只读、写入和高风险能力。
- `requiredScopes`：声明执行所需权限。
- `requiresConfirmation`：根据风险级别确定是否需要用户确认。
- `ExecutionContext`：传递 request、tenant、user、chat 和权限上下文。
- `CapabilityResult`：统一成功和失败结果。
- `CapabilityRegistry`：负责能力发现、按名称查询和重复名称校验。

本阶段已将知识库搜索作为首个渐进迁移样例，形成 `knowledge.search` Capability。它复用原有 `RagTool`，不会改变旧 Agent 的 HTTP 和对话行为，同时验证了能力元数据、执行上下文和输入校验。

#### 成效

新增能力不必先修改中央 Registry 源码即可被 Spring 发现；重复名称会在注册阶段失败；高风险能力后续可以在统一入口增加权限和确认控制。当前仍是兼容迁移阶段，存量工具尚未全部切换，SupportAgent 仍保留旧工具列表和手写分发逻辑。

### 3.6 外部调用从“直接请求”转向韧性治理基线

#### 之前的问题

地图、天气和大模型等外部服务具有网络抖动、响应超时和供应商不可用等风险。若每个调用点各自处理，容易出现超时不一致、写操作误重试和错误信息不统一等问题。

#### 采用的方法

- 引入 Resilience4j Spring Boot 依赖。
- 建立连接超时、读取超时、重试、熔断、限流和降级的统一配置方向。
- 区分只读调用和有副作用的写操作：只读调用可以进行有界重试，订单创建等写操作默认不自动重试。
- 外部事实不可用时返回明确失败，不允许模型自行猜测地图、天气或订单事实。

#### 成效

外部依赖治理从分散的调用细节提升为统一配置和策略入口，为后续按 Provider 增加独立隔离策略提供了基础。具体调用点的全面接入和降级内容仍需按地图、天气、模型分别推进。

## 4. 测试与验证变化

本阶段新增或完善了以下确定性验证：

- 订单状态机能够接受正常流程，拒绝跳过确认和离开终止状态。
- Capability Registry 能够按名称索引能力，并拒绝重复名称。
- `knowledge.search` 能够验证只读元数据、执行上下文传递和空查询失败。
- 编辑器静态诊断和 Git 差异检查可用于快速发现新增代码问题。

当前环境未安装 Maven，仓库也没有可直接执行的 `mvnw` 脚本，因此本阶段新增测试尚未在该环境中完成 Maven 实际运行。具备 Maven 环境后，建议执行：

```bash
mvn -Dtest=CapabilityRegistryTest,RagSearchCapabilityTest,OrderWorkflowStateTest test
```

## 5. 本阶段带来的实际价值

### 对用户

- 下单前确认边界更清晰，降低误下单和重复下单风险。
- 外部服务异常时更容易返回可解释结果，而不是生成未经验证的事实。
- 后续可以围绕轮椅、老人、孕妇、携童、宠物和大件行李等特殊需求增加带风险和权限信息的能力。

### 对开发者

- 新成员可以通过配置模板和 Compose 更快复现本地依赖。
- 订单规则和 Capability 注册规则可以用确定性单测验证。
- 新能力具备统一的名称、风险、权限、上下文和结果模型。

### 对运维和排障

- 有标准健康检查和指标入口。
- 订单状态迁移、工具调用和请求上下文具备进一步统一记录的基础。
- 关键外部依赖可以按统一韧性策略治理。

## 6. 尚未完成与下一步

本阶段没有将以下内容描述为已完成：

1. 维护者轮换历史上可能暴露的所有凭据。
2. 将全部存量 `@Tool` 迁移为 Capability。
3. 用 Provider 端口完全隔离 Agent 与高德、天气等具体供应商。
4. 对 `AgentEvent` 做协议版本化并完成前端联调。
5. 补齐真实 Redis、MySQL、MongoDB 环境下的并发和故障注入测试。
6. 建立完整的路由、工具调用、订单迁移耗时和失败率指标。

推荐的后续顺序是：

```text
继续迁移只读订单/工单工具
→ 抽取地图和天气 Provider 端口
→ 将 Capability Registry 接入 Agent 工具发现
→ 补充并发、超时、熔断和降级测试
→ 版本化 AgentEvent 并与前端联调
```

## 7. 阶段结论

本阶段不是简单增加功能，而是给已有多 Agent 业务链路补上生产化边界：配置可交付、环境可复现、订单可控、运行可观测、能力可扩展、依赖可治理。

项目目前已经从“能够演示完整 Agent 流程”推进到“具备生产化演进骨架”。下一阶段的重点是把这些抽象继续接入真实业务路径，并通过并发、故障和端到端测试证明它们在运行时确实有效。
